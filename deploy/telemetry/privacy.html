Privacy notice for Rynhult usage statistics and bug reports

Pre-release staging service. Rynhult is not yet publicly released. Anything received here before the version 1 launch is test data, and all of it is deleted at launch. The retention periods below already apply now.

This collector, telemetry.rynhult.dev, receives optional usage statistics and bug reports from Rynhult installations. Every installation sends nothing unless its owner turns sending on.

Who is responsible

The controller is Joshua Fulton, the Rynhult project maintainer. For any privacy request, write to privacy@rynhult.dev.

Only if an installation's owner opts in

  • Both kinds of data are off by default, and are two separate choices. Only an owner of an installation can turn them on, in Settings → Usage and bug reports. Members of an installation can't.
  • Consent is to a schema version. If a later version would send something new, sending switches off and the owner is asked again.
  • Turning a choice off stops sending at once and discards anything waiting to be sent.
  • An installation can send somewhere else, or nowhere: its operator can point it at their own collector or remove the feature entirely.

Legal basis: consent

Data is received and kept only because an installation's owner consented by turning sending on. Consent can be withdrawn at any time by turning the choice off. Sending stops at once and anything waiting is discarded. Data already sent is deleted too when the owner leaves Also delete previously sent data when turning a choice off ticked; otherwise it is kept for the periods below, and can still be deleted later (see Your rights). Withdrawing doesn't affect what was done with the data before.

Bug reports

  • Only about failures of Rynhult's own code and helpers, never about what an agent did.
  • An owner sees each report and approves it before it is sent. Unapproved reports are discarded after seven days. At most ten reports a day are sent.
  • A report holds: a random report id; the installation's report key id; Rynhult's version and kind of installation; the operating system family; what triggered it and which part of Rynhult failed; the type of error (only Python's own error names, otherwise other); a short fingerprint of the error type and code locations, to group repeats; up to 20 file names, function names and line numbers of Rynhult's own code; how often it happened that day, as a range; the error message after scrubbing, at most 300 characters; and, for a crashed session or process, which agent it was and its exit code.
  • Scrubbing removes the installation's known secrets and its known names (people, projects, repositories, machines, hosts), and anything shaped like a token, email address, network address, host name or file path. It runs before and after shortening. Scrubbing is best effort: a name or secret the installation doesn't know about, in an unusual form, could be missed. This collector scrubs again on arrival.
  • A report about a crashed session contains details about the process only, never its contents.

Never collected

Prompts, transcripts, terminal output, model outputs, file names or contents, code, paths, repository or project names, branch names, host and machine names, IP addresses in the data, usernames, email addresses, display names, keys or their names, server and catalog names, guardrail patterns, model or endpoint names, time zone, locale, exact counts and exact times. (The collector itself notes when each item arrived and when a key was last used; see How long data is kept.)

Installation keys

  • Each installation signs what it sends with keys it creates itself. Usage and bug reports use separate keys, and each is replaced every 90 days by a new, unrelated one. Rynhult sends nothing that links an old key to a new one or a usage key to a report key.
  • A key shows that data comes from the same installation as before. It identifies no person, and it doesn't prove the data comes from a genuine installation.
  • The installation keeps its old keys only to be able to ask for deletion, for at most 13 months.

Connections

This collector keeps no access logs. The address a connection comes from is used only to limit how often it may send, held in memory until the current hour or day ends, and is never stored with the data. No location lookup is done.

Your rights

Data here is linked only to installation keys, so a request names the installation's usage and report key ids, including retired ones. A host name or email address can't identify your data, so it can't be used instead. A report id alone needs a manual check that it is yours.

  • Access and portability. Email privacy@rynhult.dev with your key ids to get a copy of what is held for them, as a JSON file. A key id isn't secret, so we confirm the request is yours before sending the copy.
  • Deletion. In Rynhult, use Delete data already sent in Settings → Usage and bug reports, or leave Also delete previously sent data when turning a choice off ticked when turning a choice off. Rynhult signs the request with every key it kept, current and retired, and shows the receipt. Or email privacy@rynhult.dev with your key ids. Deletion is completed within 30 days. Monthly totals carry no key id, so they can't be traced back to an installation or removed for one.
  • Objection and restriction. Turn the choice off in Rynhult, which stops sending at once, or email privacy@rynhult.dev with your key ids.
  • Rectification. The data is generated by Rynhult rather than entered by a person, so it isn't edited; anything wrong can be deleted as above.
  • Complaint. You can lodge a complaint with a data protection supervisory authority, for example the one where you live or work.

No decision with legal or similar effect is made about anyone from this data, automatically or otherwise.

Hosting

The collector runs on a dedicated virtual machine at Akamai (Linode) in Frankfurt, Germany. Data is stored only on that machine's own disk in the EU and isn't transferred outside it for storage. During staging there are no backups beyond that disk: if the machine's disk is lost, the data is lost with it. Akamai processes the data only as the hosting provider, under a data-processing agreement. No third-party analytics or error service receives this data.
