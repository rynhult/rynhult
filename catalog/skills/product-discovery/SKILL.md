# Product discovery

Start from the person's brief, assignment and existing product. Discovery clarifies
what matters; it does not widen scope or authorize implementation.

## Read before asking

Read the pinned brief version and accessible references, existing product docs,
requirements and constraints. Preserve the person's submitted text verbatim and
keep your interpretation separate. Inventory what is already supplied; do not
re-ask those questions or substitute a new product for the requested feature.

If a reference is unreadable, name its REF-n and the limitation. Ask for the
specific missing evidence or an accessible alternative when a requirement depends
on it. Do not claim to have inspected an image from its filename or caption.

## Build the smallest useful discovery record

Cover these fields, using supplied answers first:

| Field | Outcome |
|---|---|
| audience and problem | Who needs this, what they do now and the difficulty |
| main journeys | Entry, key action, outcome, error/refusal and recovery |
| first release | Minimum coherent scope, exclusions and later ideas |
| success | Observable acceptance, not only an implementation milestone |
| design direction | Existing brand/system, accessibility and reference intent |
| constraints | Stack, platforms, integrations, compatibility, privacy, time/resources |
| uncertainty | Missing evidence and which decision it changes |

An incomplete draft or "I don't know, recommend something" is valid. Recommend a
reversible default with tradeoffs when safe; label it **assumed default** rather
than pretending it was the person's decision. Do not ask a checklist of questions
whose answers do not change the first release.

## Connect discovery to accepted work

Draft R-n requirements with source and acceptance evidence. Identify C-n
constraints without changing existing person-controlled text. Interpretation is
not acceptance: use the available brief/decision tools for proposed changes.
Keep uploaded references project-private and cite REF-n, not a copied wiki asset.

Put each material unresolved question on a decision card, with `blocks` naming
only the phase keys or R-n IDs that depend on the answer. Record options, impact
and your recommendation. Do not freeze unrelated work or silently assume a
material change to privacy, authority or scope.

## Respect the mode and report

In prepare mode, use read-only discovery and listed plan/brief/report tools.
In build mode, implementation stays within accepted scope and unblocked work.
Before readiness, account for every brief field and accessible reference, list
uncertainty and map the requested scope to requirements. Return the interpretation,
questions, defaults and verification limits through the available report route.
If tools are absent, return a proposal; do not invent an authoritative file.
