# Rynhult 0.15.0-rc.1 (release candidate, draft)

> **Draft for the public release candidate.** Not tagged or published yet. Publication and the remaining
> installation, recovery and device checks are separate from preparing these notes.

Rynhult is a **self-hosted supervisor for coding agents**. Run Claude Code, Codex and other agent CLIs on your
own machines, then watch their terminals, answer questions and review their work from a browser. It is built
for individuals and small teams using their own provider accounts.

**0.15.0-rc.1** is the first public release candidate, not the stable 1.0 release. Its scope is the
**Linux server**, the dashboard in desktop and phone browsers, and the phone web app installed from a browser.
Additional machines remain supported as nodes: **Linux, macOS and Windows through WSL2**.
The qualified main-server distributions are Ubuntu 24.04+ and Debian 13+ with systemd.

Native Windows, macOS standalone, Linux desktop, iOS and Android apps are **post-v1** work, one platform at a
time, in an order not chosen yet. Experimental native source is not a supported app release.
See [decision 0073](../decisions/0073-v1-linux-server-scope.md).

The RC is planned as a public [GitHub prerelease](https://github.com/rynhult/rynhult/releases), alongside
[rynhult.dev](https://rynhult.dev), after feature freeze. Install it deliberately on a machine you can restore.
The normal updater does not offer release candidates.

## What's in

Earlier release work is also listed in [CHANGELOG.md](../../CHANGELOG.md) under *0.15.0-rc.1*. The headlines:

- **Sessions on your machines:** Claude Code, Codex, GitHub Copilot CLI, Antigravity, Cursor and OpenCode in tmux,
  in the browser, with worktrees, Multi-run, schedules, search, live previews, pull-request feedback and an Inbox.
  Sessions can run on Linux machines, Windows PCs through WSL2, and Macs.
- **The new name:** ACC is now Rynhult. Existing installs keep working: old commands, services and paths stay, and the
  `rynhult` commands are added beside them.
- **Teams:** groups with a shared work board, claims and quotas; passkeys; members' own agent accounts.
- **Backups:** encrypted backups to a Linux receiver, S3-compatible storage with Object Lock, or a local directory;
  planned downtime and catch-up backups; receivers that check they still write to the same disk.
- **Clearer screens:** Overview shows what needs you first; Settings opens one section at a time; Host shows
  problems first; the terminal works with screen readers. Errors explain what failed and what to try without
  exposing internal exception names.
- **Add machine before the installers:** Windows (WSL) and Mac machines can be added and updated from the main's own
  source, with its certificate checked by fingerprint and the enrollment code kept off the command line.
- **Security and reliability:** a stricter command guard, safer release-build permissions, scoped uninstall
  cleanup, stronger report scrubbing and launch-time permission rechecks. Historical backup schemas with
  equivalent numeric defaults no longer cause false restore refusals; other schema checks remain enforced.

## Recent dashboard and team changes

- **Team has Overview, Working list and Settings tabs.** Decision cards offer **Approve**, **Change** and
  **Discuss**. Helpers' reports wake the lead; a conflicting working-list save offers recovery without quietly
  overwriting someone else's edit.
- **Start a brief from documents.** Upload source documents, review the proposed fields and choose what to take.
  Uploading does not approve scope or replace the saved brief.
- **Less hunting through lists:** Projects and Workspaces have sortable List tables. Inbox **Dismiss all** skips
  decisions and active alerts, with confirmation and an eight-second Undo; it hides when nothing shown is
  dismissible. Audit has a bounded search box beside its filters.
- **Publishing separates Current from Audit.** Current shows the rules in effect; Audit keeps the request history.
  Publishing checks the exact hostname before replacing a live rule, even when it is on another page.
- **Delete deliberately:** project **Delete** names what it removes and requires the exact slug. Registered folders
  and GitHub repositories stay. Workspace deletion uses the owning account's service, handles already-removed
  folders, and protects project checkouts, including local-workspace aliases. Concurrent lifecycle operations wait
  for each other and recheck before changing the folder.

Release-download verification uses the public signing key: compare both full fingerprints, verify
`SHA256SUMS.asc`, then check the listed files before unpacking. The exact commands and limits are in [Install](#install).

## Orchestrator v2

**On by default in rc.1, not a Preview.** A person still grants a bounded team
at launch; no team starts merely because the feature is available. The gate
runner still requires explicit owner approval to execute branch code.

Selection follows the **owner's ordered allow-list per task type**. The score
only breaks ties within an allow-list position; neither is a quality claim.

Every assignment has a role/profile and attributable attempts. Helpers are
disposable by default; a replacement receives earlier reports, handoffs and
branches and continues from the previous head unless explicitly started fresh.
Manual pins use the same task-specific filters and cannot widen the grant.

### Brief, launch and run mode

An optional project brief accepts a form or Markdown and captioned references
kept project-private. The person chooses read-only **Clarify and prepare**, or
**Clarify, then build within this scope**. Material questions appear on the
working list; constraints remain person-controlled and affected work is
revalidated when requirements change.

In **New project**, the optional **What do you want to build? (starts your project
brief)** answer becomes project notes and saved brief version 1 for Empty folder,
Clone repository and New GitHub repo. It keeps up to 2,000 characters, with you
recorded as author and Prepare as the initial suggestion. The GitHub repository
summary uses at most the first 300 characters; the full text stays in notes and
the brief and is exported to project Markdown. Captioned references stay private.

**Filling in the brief form is not saving it.** **Product or feature (required)**
explains what is missing before Save can proceed; trying Save with that field
empty focuses it. **Draft, not saved** and **Unsaved draft restored** identify
tab-local text, not scope the lead can read. Wait for **Saved as version N**.
Leaving unsaved changes asks for confirmation.

At **New session → Advanced → With helpers**, **Project brief version** visibly
defaults to the latest saved version. Choose another saved version or **None**;
the Launch footer names the choice. If this tab has an unsaved draft with
**Product or feature** filled in, Launch asks **Save this brief as version N and
pin it to the team?**:

- **Save and launch** saves first and pins that exact version. A failed save
  never launches a team.
- **Launch without the brief** pins None, even if an older saved version exists,
  and keeps the unsaved draft in this tab.
- **Back** returns to the form without saving or launching.

The same choice covers a draft entered only on the project page. A changed
version number requires a fresh review, not silent renumbering. If saving
succeeds but launch fails, **Launch with saved brief** retries with that version
without another save.

**Team** names the pinned version, or **No pinned project brief**. Choose a saved
version and **Apply selected brief version** to add the first pin to a running
team, change it or remove it with **None**. Later saves never silently replace a
running team's scope. Applying a brief does not change the plan's effective mode.

If you leave Task empty, a new lead gets an editable first message naming the
project and selected brief. It asks the lead to read the brief and references,
draft requirements and constraints, and put unanswered decisions on the working
list. Without a saved brief it starts discovery with you. Your own Task replaces
that default; resuming a conversation does not send it again.

**Effective run mode** lives in Plan, not in the brief's suggestion. Only a
signed-in person can widen Prepare to Build, after stopping the lead and
confirming its stop. The lead can only narrow Build to Prepare after helpers
have confirmed stops; it stops too for a read-only resume. The brief keeps
its original suggestion, and **Plan history** records who changed the effective
mode. Neither change widens the team's frozen provider permissions.

### Gates and managed capacity

Gate results bind the tested branch head, base SHA and command digest, with the
runner version recorded. A new failure passing a targeted rerun is
**retry-passed**, not a clean pass until the person accepts the lead's flake task
on the working list or a fresh gate passes cleanly. **known-flake** is limited
to the owner-managed project list and is disclosed in the PR. Original failures
remain available. **Stop team cancels running and queued gates**. At expiry the
lead has a **30-minute wrap-up** (configurable 0–120 minutes) for reporting,
plan/working-list updates and finishing stopped helpers, then stops.

Native subagents run inside their parent, use its slot/permission, are not shown
in the team tree and cannot be capped by Rynhult. They are not counted as separate
managed helpers.

Council uses managed helpers within the grant or labelled **single-session
perspectives**, never a false claim of independence in one context.
See the [Orchestrator Guide](../wiki/User-Guide/Orchestrator.md).

### Agent launches and team tools

- **Empty projects are ready for worktrees.** **Empty folder** creates its first
  README commit, so **Own worktree** and **With helpers** need no bootstrap
  session. It still creates no remote or public repository.
- **Project Git author:** missing commit author settings are filled locally from
  the project owner. Existing effective settings are kept. Review **Git author**
  on the project page before publishing: the generated default uses your
  Rynhult login name. An automatic-setup failure is reported without turning a
  saved project or otherwise usable launch into an error; set the author before
  committing. This does not bypass an offline machine or other launch checks.
- **Codex launches and branch isolation:** large profiled commands no longer
  exceed tmux's command limit. Helpers using **Can edit the project** can commit
  in their own linked worktree. Extra Git writes are confined to its worktree
  metadata, shared commit objects and private branch directory with matching
  reflogs, not main, the lead's branch or other helpers' branches. Hooks,
  configuration, packed references, the project's working folder and unrelated
  repositories stay outside that extra grant. Older flat-branch Codex teams
  must be recreated on their next launch; running sessions are not changed.
  Update both main and node software before starting new-format teams.
  Sessions sharing one account are still not a strong security boundary.
  New Codex teams also wait for their required team server at startup; its tools
  may be discovered on demand rather than listed initially.
- **Team tools:** Claude, Codex and OpenCode receive session-scoped approval for
  Rynhult's team tools; Copilot exposes its team server tools as before.
  **Plan-mode reviewers stay read-only: inspect and report, not fix.** They can
  submit findings without a prompt for every report. A Prepare lead can also
  use authorized plan/brief tools. This is not blanket approval for changes:
  in Claude Plan mode, **Merge, Restack and Gate still ask the person**, and
  Prepare mode refuses implementation regardless. Other MCP servers and
  workspace edits get no new approval. Read-only Codex teams use a prompt-by-default
  team-server policy, with per-tool approval for exact reads and reports; document
  proposals/sharing and other mutations prompt. Build-capable Codex teams retain
  the existing fixed-server approval. Copilot Plan/Ask gains no blanket allow flag.
  **Cursor and Antigravity may still
  prompt for team tools.** Start a new team to pick up changed launch settings;
  existing teams retain their saved settings.
- **Image access:** an owner checks the exact model/machine/account combination
  in **Settings → Image access** before image-dependent assignments. The generated
  check uses larger, less ambiguous characters and discloses a tolerated
  one-character code misread; coloured shapes must still match exactly. Verified
  evidence expires after 30 days or relevant software changes. Unknown is not
  image support, and a pass is not a quality claim about arbitrary images or PDFs.
  Custom endpoints and per-session containers remain unqualified by this native
  check. See [Image access](../wiki/User-Guide/Settings.md#image-access).

## Terminal input, updates and message delivery

The terminal keeps its editor, focus and unfinished composition in place during
background status refreshes and avoids unchanged PTY resize requests. Safari
uses one native-input handler so committed text is sent once, rather than replayed
from an old input buffer. Spelling corrections and inline writing suggestions
are disabled; ordinary typing, composed text, paste and control keys remain.
Hidden panels do not keep polling while you type; settled message-delivery
history refreshes less often.

When an open tab detects a changed server build, **A new version is available —
reload** appears. Save or copy unsaved edits and unsent terminal text, choose
**Reload**, then confirm; Rynhult never forces the reload. A tab still running
pre-fix JavaScript needs one manual reload before it can show future notices.
The notification worker does not provide an offline copy of the dashboard.

Focused terminal regressions cover Chromium, Firefox and Linux WebKit. They are
not physical macOS/Safari prediction-service, VoiceOver or sleep/wake
qualification, and do not prove that every source of typing latency is fixed.

**Message delivery** distinguishes queued, blocked and unconfirmed messages from
confirmed submission. An open writable terminal holds control even if nobody is
typing: switch to **Activity** and close other terminal windows to release it.
Queued messages retry automatically; **Retry delivery** checks the same message
again without adding a copy. If submission is unconfirmed, check the terminal
before **Send again after checking**; Rynhult never automatically pastes an
uncertain submission again. Changes review comments stay until their delivery is
confirmed. See [Sessions](../wiki/User-Guide/Sessions.md#messages-sent-to-the-agent).

## Machine updates and backup costs

Linux/WSL node updates verify the main's authenticated archive, shipped build
stamp and expected version without applying obsolete source-publication rules.
After a successful update and reconnect check they keep two previous
helper-created installations, rather than accumulating copies. Host shows useful
failure details and cleanup warnings.

**Older helpers can need one manual reinstall from the updated main's source.**
Retrying **Update** cannot repair the old verifier that rejects a genuine new
bundle. Keep enrollment and certificate checks; never reinstall from the old
installed source or disable TLS verification. RC builds also still require the
manual node update path. Mac updates use the generated source-install command
before v1.0; fixes handle standard Homebrew bin permissions and portable installer
logging. Actual Mac/Homebrew qualification remains separate. See
[Update an older machine](../wiki/User-Guide/Nodes.md#update-an-older-machine).

Server backup targets now default to **daily captures and weekly full restore
verification**, rather than a full repository readback and restore every hour.
Targets without stored interval choices receive these defaults on upgrade;
explicit choices and enabled/disabled state stay unchanged. Daily capture means
roughly a day's recovery-point exposure; choose hourly when needed.

The first capture, due full checks and on-demand **Test restore** still read back
data and perform an isolated restore. Other captures use metadata checks, not a
new claim of full recovery verification. **Host → Backups → Details** separates
these ages, offers schedule controls and shows transfer/request scenarios, not a
cloud price quote. Egress, requests and repository history can still cost money.

Owners can **Remove target** for an S3 target after queued/running work finishes.
This removes its active configuration, not bucket data; Object Lock can prevent
deletion until retention expires. Local history, audit records and recovery keys
remain. See [Backups](../wiki/User-Guide/Backups.md).

## Known limitations

- **Native apps are outside v1:** use the dashboard in a browser or install its web app from the browser.
  Experimental desktop/mobile source exists, including native-device enrollment on the server, off by default.
  It does not supply a qualified native app and is not needed for the phone web app.
- **Windows** runs Rynhult inside WSL2 (Ubuntu 24.04). Native Windows is not supported yet.
- **Linux:** Ubuntu 24.04+ and Debian 13+ with systemd are the qualified server targets.
  Non-Debian-family nodes, including Fedora, openSUSE and Arch, are experimental; their test packages do not
  qualify them as v1 server platforms.
- **No Windows or Mac installers in rc.1:** it is a server release candidate. The main Rynhult runs on Linux; Windows
  (WSL2) and Mac machines are added from source (see [Install](#install)).
- **Updates between candidates:** installed copies only follow stable releases. A 0.15.0-rc.1 install will be offered
  0.15.0 when it is released, but never 0.15.0-rc.2; update between candidates by hand
  (see [Upgrading](#upgrading-from-014)).
- **Add machine on a candidate:** the Windows and Mac tabs show the commands that install from your main Rynhult's
  own source; there are no installer links. A Mac's update on Host uses the from-source command too.
- **PostgreSQL installs:** **Back up and update** in Settings is refused (its backup and rollback cover SQLite only).
  Back up PostgreSQL and execution workspaces separately and update by hand.

## Known issues

Things we know about in rc.1 and haven't fixed yet. You don't need to report these, but tell us if one gets in your
way.

- **Large histories:** list queries, repeat downloads and idle-session processing have been improved. The first
  sessions list still includes the whole history, and background scans still cost CPU. Slow phone connections
  and large installations can remain sluggish; archive sessions you no longer need.
- **Other machines after an upgrade:** Host offers **Update** for them, but machines don't take a release candidate
  that way. Update each one on the machine itself using the [RC upgrade instructions](../RC-TESTING.md#upgrade-from-014).
- **Guardrails are a safety net, not a sandbox:** they check the commands an agent runs as text. With GitHub Copilot
  CLI, hook support remains a Preview without real-account qualification. Known repository settings that disable
  hooks are refused at launch, but this is not protection against everything the agent's account can do.
  See [Guardrails](../wiki/User-Guide/Guardrails.md).
- **Browser qualification:** the dashboard was checked primarily in Chromium and with automated accessibility tests.
  Focused terminal checks also cover Firefox and Linux WebKit, not a full dashboard pass in those engines.
  Physical Safari, real phones and screen readers (NVDA, VoiceOver, TalkBack) haven't been through a full pass yet.
  Settings has a known rough edge: section navigation repeats similar names for screen readers, and changing
  sections with arrow keys adds browser history entries.
- **Backup and recovery:** interrupted jobs can require stale-lock review; never unlock an active repository.
  Older Linux receivers refuse captures until their owner records the receiver disk.
  Database and git captures are not a single system-wide point-in-time snapshot.
  Restore regressions have automated coverage, but that is not proof of a completed real-host replacement drill.
  Follow [Backups](../wiki/User-Guide/Backups.md), including fencing, quarantine and verification; never bypass a refusal.
- **Device pairing (direct-public Preview):** refreshing or closing the trusted browser tab can leave a one-use
  pairing link valid until its five-minute expiry. There is no person-visible list of their pending pairings.
  Revoking one device currently signs that person out everywhere, removes their push subscriptions and cancels
  other pairings. Renew or deliberately revoke outstanding devices before completing a certificate-authority rollover.
- **Stopping automated work:** a stop request is not confirmation from an offline machine. Check the team's
  stop/cancellation evidence after reconnect. If **Stop goal** fails, read the error, retry and confirm
  **Goal status: stopped**.
- **Company sign-in pilot:** recent MFA proof is required for passkey enrollment. Clock skew, including an
  identity-provider time ahead of the server, can cause a refusal. Check clock synchronization rather than weakening checks.
- **Report privacy:** scrubbing is best effort. Review every report before sending. The report schema now refuses
  `build` and `log` fields; narrowing it does not qualify the staging collector or replace the owner's deployment check.
- **Uninstall:** if you chose Ollama during setup, the uninstaller leaves its small Rynhult settings file for Ollama
  in place.

## Install

When the RC is published, download **all four source assets** from the
[public releases page](https://github.com/rynhult/rynhult/releases):
`acc-0.15.0-rc.1.tar.gz`, `BUILD`, `SHA256SUMS` and `SHA256SUMS.asc`. Download and
inspect the public key:

```sh
curl --fail --show-error --location --output rynhult-release-key.asc \
  https://rynhult.dev/keys/rynhult-release-key.asc
gpg --show-keys --with-subkey-fingerprint rynhult-release-key.asc
```

Compare both full fingerprints with an independently trusted copy before
importing; stop if either differs:

- Primary: `0C2C E126 57BD 833F B5B5 63B2 B555 F6E1 2799 0DB5`.
- Signing subkey: `B072 4912 051F F1F2 74CD EE7F EDE4 F41B 077B D2A7`.

With the release files in the same folder, verify before unpacking:

```sh
gpg --import rynhult-release-key.asc
gpg --verify SHA256SUMS.asc SHA256SUMS && sha256sum -c SHA256SUMS
```

Stop if the signature is missing, verification fails or any checksum fails.
On macOS the checksum command is `shasum -a 256 -c SHA256SUMS`.
**Only `SHA256SUMS` is signed**; its hashes cover the listed files, not Git clones
or release tags. **The in-app updater does not verify signatures yet.**
Signing and attaching the rc.1 signature is an owner-run publication step,
not proof that this draft is already signed.
See [Security](../../SECURITY.md#verify-a-source-release).

After both checks succeed:

```sh
tar -xzf acc-0.15.0-rc.1.tar.gz
sudo ./acc-0.15.0-rc.1/deploy/acc-install
```

Both the tarball and `BUILD` must pass verification before installation. The `acc-` asset name is intentional.
Use a restorable Ubuntu/Debian test machine; follow the [tester kit](../RC-TESTING.md#before-you-install) for
requirements, certificate trust and first sign-in. Add nodes through **Host → Machines → Add machine**;
see [Nodes](../wiki/User-Guide/Nodes.md). For normal remote use, use Tailscale or another VPN, not the
direct-public Preview.

## Upgrading from 0.14

Settings → Updates never offers a release candidate, so you place the new files by hand, the same way the built-in
updater does. Follow the [full upgrade walkthrough](../RC-TESTING.md#upgrade-from-014), not the fresh-install
command above. Database migrations run on first start; no separate migration command is needed.

1. **Back up first:** `sudo systemctl start acc-backup.service`, then check that
   `/var/backups/acc/<today>/` has `acc.db` and `secrets` (or `secrets.tar.enc`). With PostgreSQL, also take your own
   `pg_dump`; this backup doesn't cover it.
2. **Check and unpack** the download next to the installed copy:
   download the tarball, `BUILD`, `SHA256SUMS` and `SHA256SUMS.asc`, verify the signature and checksums
   as in [Install](#install), then unpack the tarball into `/srv/acc/app.rc1`
   as the walkthrough describes. Make the staged files root-owned and not group- or other-writable before swapping.
3. **Swap:** `sudo mv /srv/acc/app /srv/acc/app.0.14 && sudo mv /srv/acc/app.rc1 /srv/acc/app`.
4. **Run the new setup:** `sudo /srv/acc/app/deploy/setup.sh --yes`. It keeps `/etc/default/accd` and asks nothing.
   **Don't** run `deploy/install.sh` from an unpacked folder elsewhere: the services keep running `/srv/acc/app`, and
   you'd get a mix of both versions.
5. **Other machines:** update each one on the machine itself, with the command in the tester kit's
   upgrade step 6. Host still shows **Update** for them, but a machine takes only stable releases that way, so
   for a release candidate it is refused. A Mac's row shows its own update command.
6. **Going back:** stop Rynhult, restore the backup from step 1, move `/srv/acc/app.0.14` back, and run its
   `deploy/setup.sh --yes` again. Follow [If the upgrade goes wrong](../RC-TESTING.md#if-the-upgrade-goes-wrong),
   including stopping both the service and its socket. Merely putting old source over a migrated database is not a rollback.

### Upgrade notes

Synthetic upgrade rehearsals covered SQLite and PostgreSQL 16 with existing projects, sessions, keys, devices
and consent. They are useful regression evidence, not a substitute for testing your own backup and restore plan.

For Orchestrator v2, review **Settings → Admin features** and existing server
overrides after upgrading. Default-on does not widen existing team grants or
override an explicit Off. `ACC_ORCHESTRATOR*`/`RYNHULT_ORCHESTRATOR*` switches are
optional overrides, not a three-switch enablement requirement. Gate execution
and provider quota hints retain their separate owner opt-ins.

- **No manual migration step.** Rynhult migrates the database when it starts after `setup.sh`. With
  PostgreSQL, one main migrates at a time; other mains wait for it.
- **Back up before you upgrade** (step 1). On PostgreSQL that is your own `pg_dump` or snapshot. The SQLite backup
  in Settings doesn't cover it.
- **Machines:** update the main first, then the other machines, on each machine (step 5). A machine on an older
  build keeps working; Host shows **Update** for it, which a release candidate refuses.
- **Backups:** backup targets live in the data folder, not the database, and are kept as they are.

**Downgrading** a schema below 0067 doesn't refuse, but it drops what the newer schema added:

- **0067:** native phone devices lose their key and installation data and stop working. Pending phone pairings and
  phone-bound sign-ins are deleted, so older code can't mistake them for browser ones; phones sign in again after
  the next upgrade.
- **0068:** each machine's opt-in to git backups over a public address. They are off again after a downgrade.
- **0069-0073:** all Orchestrator v2 data: working lists, NOW, plans, selections, delivery evidence, task reports, gate
  jobs and reservations.

Two older downgrades refuse rather than lose data: below 0063, while a group machine account binding reserves an
agent account; and below 0054, while company-only accounts hold passkeys.

## Optional telemetry and privacy

Usage statistics and bug-report offering are **independent, off-by-default choices** under
**Settings → Usage and bug reports**. Neither is required to use the RC or file an issue.
**Show exactly what would be sent** previews the payload locally. Enabling bug-report offering does not send
reports automatically: an owner reviews and approves each report. Scrubbing can miss unknown secrets;
review the JSON and remove anything private.

Read [the privacy note](../PRIVACY.md), the [Guide](../wiki/User-Guide/Usage-and-Bug-Reports.md) and the
collector privacy notice linked in Settings before opting in. The default collector remains a **pre-1.0
staging service**, not a qualified production deployment. Data it receives before 1.0 is deleted at launch.
You can turn either choice off and request deletion of already-sent raw data; anonymous aggregates cannot be
linked back for per-installation deletion. A public RC does not change those consent or staging limits.

## Reporting bugs

- **Public bugs:** [open an issue](https://github.com/rynhult/rynhult/issues/new).
  No repository invitation or telemetry opt-in is needed. Use the [issue template](../rc/ISSUE_TEMPLATE.md).
- **Questions and experiences:** use [Discussions](https://github.com/rynhult/rynhult/discussions).
- **From inside Rynhult (optional):** if you opted in under **Settings → Usage and bug reports**, review
  and send the in-app report when one is available. Nothing is sent without your approval.
- **Cannot file an issue?** Contact [support@rynhult.dev](mailto:support@rynhult.dev).
- **Security problems:** privately, to [security@rynhult.dev](mailto:security@rynhult.dev), or through GitHub’s
  **Security → Report a vulnerability** form if enabled. Never in a bug issue. See [SECURITY.md](../../SECURITY.md).

Include version/build, OS/browser, steps, expected and actual results, and any enabled Previews.
**Never include secrets or logs containing tokens.** Leave out private hostnames, network details and session
transcripts; check screenshots before attaching them.
