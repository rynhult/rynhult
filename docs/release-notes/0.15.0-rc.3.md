# Rynhult 0.15.0-rc.3 (release candidate, draft)

> **Not published yet.** These notes prepare the next candidate. Tagging, signing,
> attaching release assets, deployment and the coordinator's full gate remain
> separate owner-controlled steps.

Rynhult supervises coding-agent CLIs on your machines from a browser. rc.3 keeps
the v1 scope: a self-hosted Linux main, desktop/phone browsers and the phone web
app, with existing Linux, macOS and Windows-through-WSL nodes. Ubuntu 24.04+ and
Debian 13+ with systemd remain the qualified main-server targets.

## Highlights since rc.2

### Security settings
- **Settings → Security** is one editor for every configurable protection: command
  guards, custom command blocks, Allowed folders, the account tool-install check,
  provider prompts, budget checks and risk labels. Owners choose a scope —
  **Instance defaults**, a **Machine / agent account** or a **Project** — and each
  row shows its effective value and where it comes from. **Default** inherits.
- Changes are drafts until **Review changes**, which lists the exact scope,
  consequences, affected projects, retained child overrides and running sessions,
  and asks for a recent sign-in check. Only **Apply Security changes** saves.
- **Unrestricted** turns off every configurable guardrail at the chosen scope after
  an explicit review. **Restore previous settings** brings back that scope's earlier
  snapshot. A persistent **Unrestricted** or **Custom security** badge shows relaxed
  controls; session headers show the policy they were launched with.
- Loosening applies to new sessions only; running sessions keep their launch
  protections. Tightening saves immediately for new work; running weaker sessions are listed and marked **on older settings** until their stops are confirmed. Stop and start a new session with reviewed current inputs; weaker generations cannot resume. Allowed-folder switches and root lists reload without stopping agents or gates; later account-service operations use the new policy while native agents retain OS access. Target acknowledgement remains required. Filesystem grant/undo retains its separate quiescence requirement. Authentication,
  owner approvals, vault rules, OS permissions, machine isolation and audit stay
  enforced in every setting, and team agents still cannot merge pull requests or
  push to main or master.
- **Allowed folders** is edited per machine/account and stays **Pending
  application** until the target machine confirms it. Folder policy and OS access
  are separate: allowing a folder does not make it readable. A reviewed Linux
  **Grant access / Undo** flow exists for separately qualified targets; this build
  ships its service units but does not install or enable the root worker.
- Undeliverable Off previews are refused before approval. Restoring an unpublished
  change to the acknowledged setting or installer-default On removes its fence
  with audit. Any recently verified owner can review/retry a published operation;
  target status can return an expired, unstarted delivery to fresh review. Apply
  reports whether the target acknowledged the folder change.
- **Recover acknowledged policy** gives verified owners a reviewed way out when
  delivery started but a removed folder or changed account mapping prevents it
  finishing. It closes the old delivery and reloads the acknowledged roots and
  switch at a newer revision. Recovery notes and the Security link survive reload.
  New changes require an updated, recovery-capable target folder service.
- Delayed folder delivery replies cannot overwrite an overlapping recovery.
  Expired, unstarted deliveries can use Retry; **Review acknowledged folder
  policy** clears a recovered fence without requiring a fake settings change.
- The old **Guardrails** and **Tool approvals** sections link to Security; saved
  custom patterns and person/project exemptions are preserved as inherited settings.

### Sessions, terminals and teams
- Terminals can fill the whole window, keeping their reading position, on desktop
  and phone and in Grid.
- Copy from terminals: drag with **⌥ Option** (macOS) or **Shift** (Windows/Linux)
  when a program captures the mouse, then **⌘C** or **Ctrl+Shift+C**. The first plain
  drag shows a short hint, and **Select text** freezes the output as ordinary text.
- New session and team launches can choose any enrolled machine for the project's
  account, reusing or copying an authorized checkout. The choice is kept for later
  launches, schedules and brief tools.
- Team time limits are optional. Teams warn before a deadline, keep stop
  snapshots, and an expired team can be resumed after a person reviews a preview.
- Orchestrator fixes for brief exports, remote and port facts, and owner answers.

## Upgrading from rc.2

rc.2 installations on the **Release candidates** channel can update in the app:
Settings → Updates → **Check now**, then **Back up and update**. The updater
verifies the signed SHA256SUMS before installing. Two database migrations run
(team lifetimes and security settings); existing guardrail, tool-approval and
folder settings carry over as inherited values. Then use Host → **Update** for
Linux/WSL nodes; Macs keep their installer route. From rc.1, follow
[Upgrade from rc.1](../wiki/User-Guide/Upgrade-from-rc1.md) to reach rc.2 first.

Back up first anyway: built-in rollback covers default SQLite, not PostgreSQL
recovery or project workspaces.

## Known issues and qualification limits

- This candidate is not stable. Ubuntu/Debian remain the qualified main targets;
  other distributions are for deliberate unqualified testing.
- Filesystem **Grant access / Undo** requires a separately installed and qualified
  Linux helper that this build does not enable. Mac and Windows-drive targets use
  existing access only. Saved custom guardrail patterns are read-only in the
  Security editor until scoped editing lands.
- Worktrees under reviewed folder policy need administrator removal, and private
  container checkouts are unavailable with reviewed folder policy.
- Guardrails are a safety net, not an OS sandbox. Containers and direct public
  remote access remain opt-in Previews. Browser automation does not replace
  physical Safari, phone or screen-reader qualification.

## Verify the release signature before installation

When rc.3 is published, download `acc-0.15.0-rc.3.tar.gz`, `BUILD`, `SHA256SUMS`
and `SHA256SUMS.asc` from the owner-published release. Use the signed source asset,
not GitHub's automatically generated archive. Obtain and inspect the public key:

```sh
curl --fail --show-error --location --output rynhult-release-key.asc \
  https://rynhult.dev/keys/rynhult-release-key.asc
gpg --show-keys --with-subkey-fingerprint rynhult-release-key.asc
```

Compare both full fingerprints with an independently trusted copy before import:

- Primary: `0C2C E126 57BD 833F B5B5 63B2 B555 F6E1 2799 0DB5`.
- Signing subkey: `B072 4912 051F F1F2 74CD EE7F EDE4 F41B 077B D2A7`.

Stop if either differs. With all release files in the same folder:

```sh
gpg --import rynhult-release-key.asc
gpg --verify SHA256SUMS.asc SHA256SUMS
sha256sum -c SHA256SUMS
```

Stop if the signature is missing, verification fails or any checksum fails.
On macOS, use `shasum -a 256 -c SHA256SUMS`. Only SHA256SUMS is signed: its hashes
cover the listed assets, not a git clone or tag. Signatures do not prove software
is bug-free. Signing/publishing rc.3 is an owner action, not something these notes
or the version bump have performed. See [source verification](../wiki/User-Guide/Install.md#verify-a-source-release).
