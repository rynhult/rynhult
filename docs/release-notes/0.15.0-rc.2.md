# Rynhult 0.15.0-rc.2 (release candidate, draft)

> **Not published yet.** These notes prepare the next candidate. Tagging, signing,
> attaching release assets, deployment and the coordinator's full gate remain
> separate owner-controlled steps.

Rynhult supervises coding-agent CLIs on your machines from a browser. rc.2 keeps
the v1 scope: a self-hosted Linux main, desktop/phone browsers and the phone web
app, with existing Linux, macOS and Windows-through-WSL nodes. Ubuntu 24.04+ and
Debian 13+ with systemd remain the qualified main-server targets. Native desktop
and mobile applications remain post-v1; experimental source does not qualify them.

## Highlights since rc.1

- **Signed RC updates in-app.** Settings → Updates has **Release channel: Stable**
  and **Release candidates**. RC installs default to the latter; owners can install
  a newer signed candidate with **Back up and update**. Stable never offers
  prereleases, and automatic installation stays stable-only. Linux/WSL nodes can
  follow their main's exact build, including RCs, once their old helper is refreshed.
- **Verified update downloads.** Main updates and latest-release Catalog restore
  verify the signed checksum list against the installed release key before
  downloading/trusting release contents. Unknown, expired, revoked and invalid
  signatures refuse installation. A stable-only, owner-audited missing-signature
  exception never applies to an RC. Node synchronization retains its separate
  enrolled-primary bundle trust path.
- **Fewer blocked requests.** Agents learn when requests are accepted or refused.
  Authenticated replies live outside agent-writable spools; fake local reply files
  cannot manufacture approval. Working-list decisions offer one-tap choices, and
  eligible unknown image models get a scoped **Check image access** action.
  Guardrail false refusals were corrected without removing the protections.
- **Projects and uploads.** Empty GitHub repositories import correctly. Files has
  bounded upload batches and folder drops, explicit replacement choices and
  per-file outcomes; concurrent drafts remain protected. Upload alerts stay in
  their affected view. Delivery controls and brief proposals have follow-up fixes.
- **Installation fixes.** WSL's first account/password prompt, node GitHub CLI
  prerequisites and missing-CLI errors are clearer. Fedora merged-sbin aliases,
  Arch broker Git context, EL package sources, stale checkouts and openSUSE sudo
  diagnostics are corrected. Non-apt tests still require explicit opt-in and do
  not qualify those distributions as supported mains.
- **Release presentation.** The site restyle, public issue templates and published
  rc.1 release/download records are included. rc.2 remains pending publication.

See [CHANGELOG](../../CHANGELOG.md) for the merged #386–#391 and batch14 changes.

## Upgrading from rc.1

**A one-time manual step is required.** rc.1 cannot discover rc.2 as an in-app
prerelease. Follow [Upgrade from rc.1](../wiki/User-Guide/Upgrade-from-rc1.md),
not repeated checks or setup.sh from a new checkout over the existing app.

1. Schedule a quiet period, keep a second administrator shell, back up the
   database, matching secrets/configuration and project data, and verify the
   signed release files before unpacking. PostgreSQL needs its own consistent
   backup, tested restore and schema-recovery plan.
2. Upgrade the main first. Source-bundle SQLite installations use the new verified
   local upgrade transaction; git installations keep their independently reviewed
   pull/install route. The bundle helper refuses git installs and PostgreSQL.
3. Check the intended version, published BUILD, health, projects, Inbox, teams and
   backup targets. Retain the source/database recovery material and rollback ID.
   An older source tree over a migrated database is not a rollback.
4. Refresh Linux/WSL rc.1 node helpers manually once, from the verified rc.2
   source, preserving enrollment and accounts. Then Host's **Update** can sync the
   main's exact installed build, including RCs. Mac nodes use their installer as
   the signed-in user, without sudo.
5. For subsequent main RC updates, choose **Release candidates**, save and
   **Check now**, then deliberately choose **Back up and update**. Automatic
   installation remains stable-only. Nodes never independently choose a newer
   GitHub release.

The Guide contains the exact staging, verification, backup and rollback commands.
For fresh installs and tester checks, use [RC testing](../RC-TESTING.md) and its
[checklist](../RC-TESTING-CHECKLIST.md).

## Known issues and qualification limits

- This candidate is not stable. Full release gates and real-machine upgrade,
  rollback, service/SELinux and provider-account checks remain separate from
  these preparation notes. Do not infer qualification from a local test result.
- Ubuntu/Debian remain the qualified main targets. Fedora, AlmaLinux/Rocky, Arch
  and openSUSE fixes support deliberate unqualified testing; openSUSE's broad
  sudo authorization must be corrected by its administrator before adding agents.
- rc.1 needs the manual hop above; its old node helper is not a reliable first
  RC update path. A Mac still uses its manual installer/update command.
- Built-in backup/update rollback covers default SQLite, not PostgreSQL recovery
  or project workspace rollback. Keep independent, tested recovery copies.
- Large histories can still be expensive. Browser automation does not substitute
  for full physical Safari, phones or screen-reader qualification. Copilot hook
  support and native-platform behavior retain their documented qualification limits.
- Containers and direct public remote access remain opt-in Previews. Guardrails
  are a safety net, not an OS sandbox. Optional telemetry and bug-report offering
  stay off by default and independent; inspect reports before sending them.

## Verify the release signature before installation

When rc.2 is published, download `acc-0.15.0-rc.2.tar.gz`, `BUILD`, `SHA256SUMS`
and `SHA256SUMS.asc` from the owner-published release. Use the signed source asset,
not GitHub's automatically generated archive. Obtain and inspect the public key:

```sh
curl --fail --show-error --location --output rynhult-release-key.asc \
  https://rynhult.dev/keys/rynhult-release-key.asc
gpg --show-keys --with-subkey-fingerprint rynhult-release-key.asc
```

Compare both full fingerprints with an independently trusted copy before import:

- Primary: `0C2C E126 57BD 833F B5B5 63B2 B555 F6E1 2799 0DB5`.
- Signing subkey: `B072 4912 051F F1F2 74CD EE7F EDE4 F41B 077B D2A7`.

Stop if either differs. With all release files in the same folder:

```sh
gpg --import rynhult-release-key.asc
gpg --verify SHA256SUMS.asc SHA256SUMS
sha256sum -c SHA256SUMS
```

Stop if the signature is missing, verification fails or any checksum fails.
On macOS, use `shasum -a 256 -c SHA256SUMS`. Only SHA256SUMS is signed: its hashes
cover the listed assets, not a git clone or tag. Signatures do not prove software
is bug-free. Signing/publishing rc.2 is an owner action, not something these notes
or the version bump have performed. See [source verification](../wiki/User-Guide/Install.md#verify-a-source-release).
