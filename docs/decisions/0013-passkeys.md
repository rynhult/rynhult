# Local passkeys and recovery

2026-10-23. Implements the local identity part of Organizations; SSO and remote device pairing remain separate work.

## Decision

Use pinned `webauthn==3.0.1` (Duo Labs py_webauthn, BSD-3-Clause), with exact versions and artifact hashes in `uv.lock`. It is a small Python verifier (the published wheel is about 74 KB), with cryptography, CBOR and ASN.1 dependencies. Its maintained releases include malformed-attestation and duplicate-CBOR-key fixes. Prefer this implementation over handwritten WebAuthn cryptography or the broader authenticator/client functionality of python-fido2. No PQC optional dependency is enabled.

A focused integration security review covered the pinned registration and authentication verifiers, client-data parser, CBOR parser, origin/RP checks, user presence/verification, signature and counter checks. This is a source review for this integration, **not an independent third-party audit or certification**. No independent audit report was found. Upstream references: [release](https://github.com/duo-labs/py_webauthn/releases/tag/v3.0.1), [registration](https://github.com/duo-labs/py_webauthn/blob/v3.0.1/webauthn/registration/verify_registration_response.py), [authentication](https://github.com/duo-labs/py_webauthn/blob/v3.0.1/webauthn/authentication/verify_authentication_response.py), [CBOR](https://github.com/duo-labs/py_webauthn/blob/v3.0.1/webauthn/helpers/parse_cbor.py). ACC additionally rejects cross-origin ceremonies; the upstream verifier does not enforce that application policy.

Use discoverable credentials, required user verification and `none` attestation. No hardware provenance is claimed. A verified passkey supplies possession and local user verification, replacing password + TOTP. Zero counters are supported; nonzero counter regressions are rejected by the verifier. Store public credential material, RP hostname and an opaque random per-user handle tied to the immutable local User ID. Future SSO identities must link to that principal explicitly. A passkey is not a remote pairing identity, provider login or API token.

RP ID is the hostname of the exact request Origin after checking `ACC_ALLOWED_ORIGINS`; HTTPS is required except loopback development. Never trust proxy Host/Forwarded values for RP selection. Distinct configured private/public names have separate enrollment; no parent-domain RP scope. Private CA use requires browser trust in Caddy's server certificate. Address changes need deliberate reenrollment.

Persist short-lived single-use challenges bound to purpose, origin, client address, browser ceremony cookie and (for authenticated operations) login session and user. Consume before verification, including failed verification. Limit pending challenges and credentials; share the existing login address/account throttles. Reauthentication lasts five minutes and belongs to one login session. Required policy permits passkey reauthentication only. Existing sessions retain their normal lifetime when policy changes.

## Recovery and policy

Allow is the default for owners and members independently. Password + replay-resistant TOTP remains available under Allow. Require refuses activation unless every affected owner has two passkeys at the current address, every affected member one, and everyone affected has a recovery code. Removal cannot reduce these minima under Require. Owners must use separately controlled authenticators for meaningful redundancy; ACC cannot prove independence of synced keys without attestation.

A person generates a random 256-bit one-use offline recovery code after recent two-factor reauthentication. Only its SHA-256 digest is stored. Replacement invalidates the old code; the browser shows the new value once outside query caches and returns `Cache-Control: no-store`. Password **and** this code recover without any remaining passkey. Recovery revokes all that person's passkeys, challenges, open reset links and sessions, closes terminals, consumes the code, changes owner policy to Allow when recovering an owner, and creates a normal session. Only an owner can use recovery to relax owner policy; the UI explains this before use. A member under Require must ask an owner to explicitly Allow member fallback before recovery proceeds. Member recovery never changes policy, and a blocked attempt does not consume the offline code. Reenroll and generate fresh recovery material, then deliberately reenable Require. Recovery creates an ordinary session; a lost TOTP device can be replaced with an owner-issued reset link under Allow. The sole owner can issue their own link from the recovered session, enroll a new authenticator and then reauthenticate for replacement passkeys. Losing the password and recovery material as well still needs a trusted host operator; this feature cannot recover secrets the person has lost.

Invite completion and owner-issued password/TOTP resets cannot bypass Require: an owner must explicitly select Allow for the affected role before joining/resetting. Resets revoke old passkeys and recovery material as well as sessions. Role changes into a required role require that role's enrollment minimum and a recovery code. This preserves the existing owner-mediated reset path without quietly weakening policy.

## Consequences

No email recovery or automatic policy downgrade on ordinary login. Recovery codes are high-value offline secrets; do not photograph them into shared artifacts. Auth events contain outcomes and actor names, never credential responses or recovery codes. The current installation API bearer remains a fully trusted local operator credential, but cannot enroll human passkeys or satisfy recent human reauthentication. SSO, device certificate enrollment, external audit export, policy ceilings and HA fencing remain their separately approved designs.
