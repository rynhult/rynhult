# CT-05 on systemd 255

## Decision and scope

There is a sound kernel-level equivalent of the root-owned parent namespace on
Ubuntu 24.04's systemd 255, Podman 4.9 and kernel 6.8: create it in the protected
root bootstrap instead of asking systemd for `PrivateUsers=full`. This preserves
the existing held rootfs design. It does not claim live runtime qualification.
No image/store/mount installation or privileged experiment was performed here.

The launcher starts a root transient service in `/`, with PID 1's private mount
staging, held read-only rootfs and private runtime tmpfs unchanged. The isolated
Python guard performs only fixed setup before running any agent program:

1. Validate its exact unified cgroup path and open all ancestors and the three
   delegation controls without symlinks. Hand ownership of only the unit directory,
   `cgroup.procs`, `cgroup.threads` and `cgroup.subtree_control` to the session UID.
   Ancestors and resource ceilings retain root ownership. This replaces the
   ownership systemd assigned when the service itself used `User=agent`.
2. Hold `/proc/self` and fork a short-lived root mapper. The service unshares only
   `CLONE_NEWUSER` while its effective UID is still zero. The mapper remains in
   the launcher user namespace and writes `0 0 4294967295` to both maps through
   the held proc directory. Mapping does not require subordinate ranges for root.
   The handshake has timeouts; failures refuse execution. Reap the mapper before
   dropping privilege. A dead target's proc descriptor cannot select a reused PID.
3. Verify a different user namespace, full identity mappings, and kernel-reported
   owner UID zero. Clear supplementary groups and all real/effective/saved GIDs
   and UIDs, then recheck namespace and real/effective/saved/filesystem IDs and
   require zero inheritable, permitted, effective and ambient capabilities.
4. Exec the fixed Podman binary as the agent, with fresh private graphroot,
   runroot, tmp and XDG state. No host-account pause namespace or image-ID lookup
   selects the execution root. Environment expansion by systemd is disabled so
   grant arguments remain literal.

This is an inference from the kernel permission model and implementation, not
an assertion based on a successful privileged launch. The brief mapper and guard
join the trusted computing base; Python and its standard library, libc, systemd,
Podman, crun and the kernel remain trusted. The guard is not setuid and is loaded
with `python3 -I` from the existing protected launcher root. The launcher refuses
a writable or symlinked guard ancestor before scheduling any root execution.
`NotifyAccess=all` remains intentional: systemd 255 accepts conmon's notification
and main PID when it belongs to the service cgroup, even though the bootstrap
started as root and conmon runs as the agent.

## Why this preserves the boundary

Linux records the creator's effective UID as the owner of a new user namespace.
A process in the parent namespace with that UID has capabilities over the child;
therefore creating it after becoming the agent is insufficient. Creating it as
root prevents the outside agent, including its `podman unshare` processes, from
acquiring capabilities over the service's user namespace or descendants. Having
the same host numeric UID after privilege drop does not itself satisfy ptrace's
cross-user-namespace capability check. It cannot open the service's proc-root/fd
aliases or enter its namespaces. PID 1's mount namespace is retained, with no
service capabilities in its owning initial user namespace.

The original host tree stays root-owned. The agent has neither ownership nor
initial-user-namespace capabilities to change its files. Within execution, the
held rootfs bind is read-only and ancestor-created mounts cannot be made writable
by the rootless child. Runtime storage lives behind the root-owned namespace
boundary, preventing a same-UID outsider from replacing Podman's runtime view.
The image directory FD remains held across PID 1's bind and synchronous launch;
execution uses that mount, not another mutable name or image-ID lookup. As
before, root must not edit/replace published trees during active sessions: a
directory FD pins an object, not an immutable snapshot of its descendants.

## Candidate evaluation

| Candidate | What works | Cost | What it cannot guarantee alone |
|---|---|---|---|
| Root-created idmapped read-only mount | Kernel 6.8 supports idmapped mounts on supported filesystems. Root can clone/hold a tree, apply an idmap and read-only flag, and pass the mount. A mapping can present root ownership appropriately without chowning backing files. | Root mount helper, filesystem checks, mapping lifecycle and mount-lock/alias qualification. Podman 4.9's own `idmap` option is rootful-only; root must do this work. | Mapping changes permission interpretation, not the runtime's owner or image authenticity. Mapping ownership to the agent makes writable aliases especially dangerous. A detached read-only view without namespace isolation does not stop an outside same-UID actor controlling an agent-owned runtime namespace. Sound as a component with root-held immutable source and protected runtime, unnecessary here. |
| Root-owned overlay lowerdir through FD | A held root-owned lower tree can bind execution to its source. Root can construct an overlay and hold its mount. | Extra overlay/kernel API integration, upper/work lifecycle and storage/runtime changes. On 6.8 the overlay parameter interface takes lowerdir names; a held `/proc/PID/fd/N` alias is a pathname technique, not a Podman 4.9 lowerdir-FD option. | A protected lowerdir does not protect a writable upperdir or prevent whiteouts/copy-up substituting executed files. Rootless runtime controlled by the outside same UID remains unsafe. A root-held read-only overlay with the namespace boundary can work, but adds nothing to the flattened held rootfs used here. |
| Hash tree at launch, execute held mount | Trusted expected digest plus complete metadata-aware verification of a protected tree detects tampering. Holding and executing the same protected mount avoids a second lookup. | Full-tree I/O per launch, canonical manifest for content, links, modes, xattrs and all execution-relevant metadata. | A directory FD or read-only bind does not freeze files writable through another alias; hashing a mutable tree leaves a race. It also cannot stop later runtime view substitution by a same-UID controller. Existing verified owner publication and immutable-to-agent ownership avoid those problems without a repeated hash. |
| crun `--root`, protected storage, agent store disabled | Explicit runtime state/configuration reduces accidental selection of account-controlled state. | New bundle/state handling if bypassing Podman; rootless Podman still needs writable runtime metadata. | crun `--root` selects its **state directory**, not the container rootfs or image trust policy. Root-owned storage alone does not create a same-UID process/namespace boundary. A permanently non-writable state directory cannot serve as rootless crun's writable state. |
| Dedicated per-session system user | A distinct host UID and disjoint subordinate ranges can isolate the original account from runtime processes/state. With a root-held protected rootfs and no writable image aliases, this is sound on 255. | Account/subuid/subgid allocation and cleanup, UID reuse protection, home/runtime lifecycle, revised grants/broker/ownership, workspace and secret access, cgroups and auditing. This is an architectural change rather than a launcher switch. | A new UID alone does not authenticate the tree or prevent name races; it still needs held execution source and protected backing files. Sharing writable image files or allowing reuse while processes remain breaks the boundary. |
| Protected root bootstrap (chosen) | Recreates the required root-owned full parent user namespace with existing 6.8 kernel APIs and retains held rootfs execution. | Small root mapper/guard and explicit narrow cgroup delegation; non-root protocol tests plus mandatory owner runtime qualification. | Does not defend against root changing the tree, kernel/runtime vulnerabilities, or mutable workspace content. Does not prove distro-specific live Podman/AppArmor/cgroup behavior without owner qualification. |

If bootstrap, map/identity/owner verification, cgroup validation or runtime setup
fails, launch stops. There is no boolean `PrivateUsers=yes` fallback: systemd
255's boolean mode maps root and the service identity, not the full subordinate
ranges needed by this rootless keep-id runtime. There is no account-store retry.
The least disruptive alternative if live qualification fails is to keep container
mode disabled pending diagnosis or an owner-approved systemd 258 upgrade. A
separate service user is the sound larger redesign, not a weaker mount-only fix.

- [systemd 255 execution documentation](https://github.com/systemd/systemd/blob/v255/man/systemd.exec.xml): boolean PrivateUsers semantics.
- [systemd 255 command construction](https://github.com/systemd/systemd/blob/v255/src/run/run.c): command environment expansion and transient execution flags.
- [systemd 255 notification handling](https://github.com/systemd/systemd/blob/v255/src/core/service.c): suitable main PIDs and notification access.
- [systemd 255 cgroup delegation](https://github.com/systemd/systemd/blob/v255/src/shared/cgroup-setup.c): `cg_set_access` limits delegation to the directory and control allowlist.
- [Linux 6.8 user namespace implementation](https://github.com/torvalds/linux/blob/v6.8/kernel/user_namespace.c): creator ownership, full mapping and parent capability checks.
- [Linux user namespaces](https://man7.org/linux/man-pages/man7/user_namespaces.7.html) and [ptrace checks](https://man7.org/linux/man-pages/man2/ptrace.2.html): parent ownership and cross-namespace access rules.
- [Linux 6.8 mount implementation](https://github.com/torvalds/linux/blob/v6.8/fs/namespace.c) and [idmappings](https://docs.kernel.org/6.8/filesystems/idmappings.html): mount ownership, idmapping checks and read-only locking.
- [Linux 6.8 overlay parameters](https://github.com/torvalds/linux/blob/v6.8/fs/overlayfs/params.c) and [overlay documentation](https://docs.kernel.org/6.8/filesystems/overlayfs.html): lowerdir selection and copy-up semantics.
- [Podman 4.9.3 run](https://docs.podman.io/en/v4.9.3/markdown/podman-run.1.html): rootfs, rootless user namespaces and rootful-only idmap.
- [crun 1.14.1 manual](https://github.com/containers/crun/blob/1.14.1/crun.1.md): `--root` is runtime state storage.
- [util-linux 2.39 unshare](https://github.com/util-linux/util-linux/blob/v2.39/sys-utils/unshare.c): range options invoke newuidmap/newgidmap. We do not assume these helpers exempt root from configured subordinate ranges; the protected mapper writes kernel maps directly.
