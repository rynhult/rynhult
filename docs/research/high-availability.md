# High availability and clustering for ACC

Design review, 2026-10-22. Owner request: “We're running on a single node, but if companies are adopting this they need a realistic capability to set up multiple 'main' nodes that sync.” This is a proposal, not an implemented capability or an approved architecture decision.

## Finding

Build recoverability first, then one logical ACC with PostgreSQL and an active-passive control plane. Add concurrent dashboards only after commands, machine connections and files have explicit ownership. Independent ACCs with a combined view are a separate federation product.

ACC already separates control from execution: accd owns desired state; per-account brokers execute commands; native agent processes run in tmux ([architecture](../wiki/Internal/Architecture.md#L3), [supervisor](../../src/acc/server/supervisor.py#L1)). Multi-host currently means **one primary, many execution machines**, not redundant primaries ([design](../MULTIHOST.md#L1)). The enterprise organizations item already anticipates PostgreSQL and multiple dashboards in the approved organizations proposal.

Citations below are repository-relative paths with source line numbers at review time. “Proposed” describes future work. RPO means recoverable data loss; RTO means time until useful service returns. Estimates are planning judgments, not measured guarantees.

## What fails when the main dies today

| Failure | What continues | What is unavailable or lost |
|---|---|---|
| accd process failure, host healthy | Local and remote tmux sessions; brokers; existing Caddy routes and running site processes | Dashboard/API, terminals through ACC, supervision, polling, notifications, new launches and approvals until restart. Broker refresh itself preserves tmux ([updates](../UPDATES.md#L40)). |
| Whole main host failure | Sessions on other machines, subject to those machines/provider availability; local hooks continue to spool | All main-host sessions stop executing. Dashboard and control of all machines disappear; no automatic recovery, scheduled git copies, key cleanup or policy evaluation until control returns. Main-host sites and proxy disappear. Remote agents may keep working or wait at a prompt. |
| Main disk unrecoverable | Remote worktrees, transcripts, spools and agent logins remain on their machines | Local uncommitted work, local transcripts/run files and changes since last successful backups may be gone. Git backup stores committed refs, not dirty trees, provider identity or local workspace projects ([limits](../MULTIHOST.md#L215)). |

Nodes reconnect to **one configured URL**, with 1–60 second backoff, not to another main ([client](../../src/acc/node/client.py#L235), [config](../../src/acc/node/config.py#L49)). Restoring the DB preserves enrolled public keys as of that backup; newer enrollments are absent and later revocations can be rolled back. Treat that as a security recovery issue: review/revoke identities and credentials changed since the snapshot before reopening access.

Today's daily helper takes an online integrity-checked SQLite backup, then secrets, overlay, git and optional user mirrors; keeps 14 days. Timer is 04:30 with up to ten minutes jitter, and installation does not enable it automatically ([backup](../../deploy/backup/acc-backup#L160), [timer](../../deploy/backup/acc-backup.timer#L5), [install](../../deploy/install.sh#L160)). This is not an atomic snapshot of all state. Runs are excluded. Secrets encryption is optional and does not encrypt plaintext TOTP/model keys in the DB or code in git ([backup scope](../../deploy/backup/acc-backup#L2)). A different drive on the same dead machine is not off-host disaster recovery.

With a verified enabled daily backup, DB RPO is roughly one backup interval, potentially longer after failures. Git recovery from the daily copy also depends on the last successful project push (normally checked for changes every 15 minutes). Remote projects can supply newer commits after reconnect; don't promise complete recovery. No tested replacement-host RTO was found. **Hours to a day is a planning allowance**, dependent on hardware, backup access, credentials, DNS/TLS, reinstall and data volume; not an observed result. If backups were never enabled or accessible, no bounded recovery exists.

The existing [restore procedure](../wiki/Internal/Operations.md#L88) covers restoring a database on an installed machine. Proposed cold-restore scripting must additionally fence the old host, select/validate a complete backup manifest, install matching trusted build, restore ownership and all secrets/overlay/git, remove stale WAL/SHM while stopped, restore configuration/trust, route the stable name, then reconnect and inspect machines before enabling reconcile. Restore passphrases must be available outside the failed host. Never let an older DB relaunch previously stopped work without reconciliation review.

## Options

Effort: S = bounded recovery/documentation work; M = several coordinated subsystems; L = architectural work across persistence, protocol, security and deployment. These are relative scopes, not delivery dates. Every option retains independent off-host backups and restore drills.

| Option | ACC changes and operation | Failure / split-brain | Security and burden | Effort |
|---|---|---|---|---|
| Cold standby from backups | Script the replacement-host procedure above; preserve stable endpoint and TLS identity; inventory execution-host backups separately. Spare can be preinstalled but accd stays stopped. | Manual fence, restore and cutover. Lose changes since backup; remote tmux survives. Old host must never restart as a second authority. | Encrypted off-host backups plus protected recovery credentials; isolated restore drills and a named operator. Least ongoing complexity. | S for runbook/script; M for reliable full-host drills |
| Warm standby, streamed SQLite | Litestream restores an asynchronously streamed DB into an inactive standby; LiteFS instead offers a single-writer replicated filesystem with lease-based primary selection. Also replicate secrets, overlay and git with consistency manifests. Keep standby app/loops inactive until promotion. | Async lag can lose acknowledged writes. Manual promotion first: fence old primary, check replication positions and file readiness, promote and reroute. Automatic promotion needs external quorum/fencing, not just two hosts pinging each other. Never merge divergent databases. | More machines/storage hold secrets. Litestream needs protected replica-store access; LiteFS adds filesystem/lease infrastructure. Test ACC transaction patterns and migration startup on chosen version. | M manual; L automatic end-to-end |
| Active-passive, shared PostgreSQL | Both mains installed; one active controller, shared transactional DB, replicated/versioned files and secrets, stable front door. Dedicated PostgreSQL advisory-lock connection elects scheduler; API actions also use durable command claims/fencing. Replace SQLite engine, migrations/search specifics; serialize schema migrations. | App failover retains committed DB state if DB survives. DB is a new single point unless itself HA. Loss of DB/leadership stops control writes; remote execution continues. Old commands in flight require broker fencing despite lock transfer. | TLS and least-privilege DB access, protected secret distribution, managed DB backup/PITR. Moderate app operation; substantial persistence migration. | L |
| Active-active dashboards over PostgreSQL | Load balancer serves multiple APIs; shared DB, global throttles/terminal leases, shared or versioned files; node connection routing and machine command ownership. Leader schedules loops; workers claim durable jobs. WebSockets stay on their connection owner; requests route internally to that owner. | Another API accepts reconnects; terminals break and reattach. Minority/DB-disconnected controllers fail closed for commands. DB, edge, file service and connection router must each have a failure plan. Leader loss must not duplicate launch/stop/publish/backup. | Every API is a privileged control server. Authenticate internal RPC; preserve per-person permissions, CSRF/Origin, accurate client IP and private-network restriction through LB. Highest deployment/testing burden. | L, materially larger than passive |
| Independent ACCs federated into one view | Each site retains its own DB, vault, enrollment, control and failure domain. Aggregate authorized read views with namespaced site/resource/user identities; later route explicit actions to the owning site. | WAN outage leaves each site's dashboard/control working; combined view shows stale/offline data. No automatic session or state takeover; no multi-writer DB conflict because sites own separate objects. | Site-scoped credentials, explicit identity mapping and audit provenance; avoid copying site secrets centrally. Federation gateway compromise must have bounded site access. | M read-only aggregation; L cross-site control |

Vendor facts checked against primary documentation: [Litestream](https://litestream.io/how-it-works/) describes asynchronous disaster-recovery replication; [LiteFS architecture](https://github.com/superfly/litefs/blob/main/docs/ARCHITECTURE.md) describes leases and asynchronous replication, with promoted primary state authoritative. Neither replicates ACC's non-database files or fences ACC broker actions. PostgreSQL offers [session and transaction advisory locks](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS); ACC must supply the job/command protocol around them. No version-specific integration or compatibility was tested here.

## Ownership and failover protocol

### Finding the new primary

First use a stable `https://acc.example.lan` endpoint moved by an operator or redundant edge. Preserve certificate trust and configured Origin/cookie hostname. DNS TTL and existing WebSockets still affect reconnection time; the edge must itself be redundant for HA.

Later let enrollment contain several approved primary URLs and either a pinned set of CA fingerprints or a cluster identity binding endpoints to an authorized cluster. Maintain chain **and hostname** verification. Distribute pin rotations with an overlap period through an already trusted channel, with an offline recovery method. Never trust a new CA just because a server answering DNS offers it. Apply the same endpoint/trust policy to node bundle downloads and git pushes, including root-owned update configuration.

Today a node signs a nonce plus the server-supplied primary id; `NodeHub.primary_id` defaults to random per process and the node signs the challenge's id ([identity](../../src/acc/node/identity.py#L49), [hub](../../src/acc/server/nodes.py#L294)). This authenticates the node to the TLS-authenticated server; it is **not** persistent cluster identity or leader authorization. Proposed enrollment must atomically consume a code across instances, share revocations, and bind the enrolled node to the cluster. Replicate public node records, not node private keys.

A node connected to any main needs an authenticated connection directory: node → connection owner → current control leader. It can retain one outbound link and fail over URLs; it need not accept concurrent controlling links. Leader epoch and command ids travel to the broker/execution boundary; reject stale epochs and return prior results for retried ids. A cluster-wide epoch must be durably monotonic across database recovery too. Without that protection, an isolated former leader can still act on an existing socket after a new leader takes over.

### The failed main's own sessions

Replace `host=local` with a stable execution-machine identity before enabling failover. Otherwise the new primary interprets the old main's sessions as its own local sessions and can launch into the wrong host/account/path. Keep existing local paths tied to the original machine; migrate records deliberately ([host dispatch](../../src/acc/server/reconcile.py#L22), [models](../../src/acc/server/models.py#L35)).

Prefer dedicated execution nodes for company workloads. A main may also execute, but model it as a node. If only accd failed, reconnect its broker and adopt the existing pane. If the whole execution host failed, mark it unavailable and preserve desired state; do not start a duplicate elsewhere. After reboot, resume the same native conversation only where transcript, workspace, account credentials and compatible run layout exist. Permanent loss requires explicit operator recovery; missing transcript means Recovery needed, never a silent replacement conversation ([resume](../../src/acc/server/reconcile.py#L202)).

### Loops, updates and backups

A leader lock alone is insufficient: a pause or DB disconnect can leave an external operation in flight. Use a dedicated leadership connection, stop dispatch immediately on lock loss, and require durable job claims, idempotency keys and fencing at effect boundaries. Gate API-triggered launches, publishes, account/package helpers and manual backup/update requests too. Proposed outboxes atomically record intent with state changes; workers record completion and reconcile ambiguous results after a crash. Ingest deduplicates source events rather than assuming a file offset gives exactly-once effects.

Updater today backs up, installs, checks health and can restore the pre-install SQLite database ([update design](../UPDATES.md#L23), [entry point](../../deploy/updates/acc-update#L1)). In a cluster, one coordinator upgrades a passive server first, fences promotion of incompatible builds, then switches leadership and upgrades the other. Migrations run once under a deployment lock; use expand/contract schema changes. **Never restore an old shared database as a local server rollback while other mains write.** Schema/data recovery is a separate cluster operation. Node followers must follow the chosen cluster release, not whichever mixed-version main they reached.

Daily backups need a designated scheduler or unique destinations per host and a manifest proving completion, DB position/schema, key versions, overlay revision and git snapshot. Retain immutable generations; current date-named directories are overwritten on repeated same-day runs ([backup](../../deploy/backup/acc-backup#L160)). PostgreSQL needs its own consistent backup/PITR and restore procedure; replication does not protect against mistaken deletes or corruption propagated to replicas.

Git backup scheduling remains leader-owned initially, with one receiver and per-project durable claims. Route both discovery and receive HTTP to that receiver (or share scoped token validation safely), preserve append-only hooks and project identity, and coordinate snapshotting with receive/maintenance. After promotion, abandon stale push tokens and retry with new ones. Record repository replication lag separately from DB lag; do not report a backup healthy merely because its DB observation replicated.

## Recommended stages

1. **Recoverable single main.** Ship a complete state/backup manifest, encrypted off-host generations, replacement-host restore script, operator fencing checklist and regular isolated recovery drill. Make backup age/failure visible. Separate execution-host loss from control-plane loss. Agree RPO/RTO before claiming enterprise availability.
2. **Company baseline: PostgreSQL active-passive.** Retain SQLite for simple single-main installs; support PostgreSQL as the company deployment backend, not two different HA products. Add stable machine identities, durable command/outbox and ingest deduplication, leadership/fencing, secure versioned files/secrets and a stable TLS endpoint. Start with manual promotion; publish measured drill results. Use a managed or otherwise independently HA PostgreSQL deployment so moving the database does not just relocate the failure point.
3. **Automatic failover, then active-active APIs.** Add quorum-backed promotion/fencing, dependency readiness, file lag checks and failure-injection tests. Then add connection routing, shared security limits and terminal arbitration, cross-instance cache invalidation and redundant edge. Allow every node to reach any main. Scale dashboards independently from execution ownership.
4. **Federation if sites need autonomy.** Start read-only. Keep independent site authorities and disclose stale data. Choose it for disconnected-site operation, not as a synonym for failover of one ACC.

A manual Litestream standby is a reasonable interim project **if recovery drills show daily backup RPO is inadequate before PostgreSQL is ready**. Do not promise active-active SQLite, and do not invest in automatic SQLite promotion unless that becomes an explicitly funded long-term deployment target. Supporting both DBs requires parity tests, dialect-specific migrations/search adapters, import/export validation and documented feature boundaries; SQLAlchemy models alone do not establish portability.

### Rules to adopt now

- No new correctness/security state solely in process memory without an ownership, restart and multi-instance plan. Label caches as rebuildable and define invalidation.
- Every external effect has a durable intent, stable id, owner, retry policy and recoverable result. No cross-process correctness based only on `asyncio.Lock`.
- Stable cluster, execution-machine and resource identities; no implicit “this server” for persistent workloads. Namespace resources for future federation.
- Separate API, scheduler and execution capabilities. Readiness includes leadership where required, schema/build compatibility, secret availability and file revisions, not just HTTP health.
- Treat DB and filesystem changes as separate failure boundaries; prefer transactional metadata plus immutable/versioned files. Measure each replication stream's lag.
- New deployment features include restore, failback, partition and stale-leader tests. Test duplicate commands, lost replies, leader pauses, revocations, concurrent TOTP, node reconnection and rollback with running remote sessions.

## Questions for the owner

1. Does “multiple mains” mean one logical company ACC with failover, or independent sites that must work during WAN outages? Is a combined view enough initially?
2. What loss and outage are acceptable: minutes versus a day of metadata, and minutes versus hours without dashboard control? Which failures must be covered: process, host/disk, whole site, or operator error?
3. Can company installs require PostgreSQL and a redundant edge, preferably managed, while personal installs keep SQLite? Who operates and drills recovery?
4. Can company workloads run on dedicated execution nodes? Should main-host work be excluded from availability promises, or is restoring provider transcripts/worktrees part of the product?
5. Are additional control servers allowed to hold all vault, provider endpoint, identity and DNS secrets? Is an external secret manager/customer PKI required?
6. Is manual promotion acceptable for the first release? Who may fence/promote/fail back, and what independent authority can prove the former primary cannot issue commands?
7. How should restoration of old enrollment/revocation/approval data be handled? Must audits stream externally so rollback cannot erase security evidence?
8. Is multi-site data residency required? Which state may cross sites, and must work continue without central identity/DB access?

## Verification limits

This review inspected the requested architecture/security/operations documents, multi-host/vault/update/orchestrator designs, listed server modules, node package and deployment installer/Caddy/broker/backup paths. Designs can be ahead of implementation; especially orchestrator capability is not assumed shipped. No running deployment, backup availability/age, replacement-host restore, replication integration, network partition, PKI rotation or measured RPO/RTO was verified. No code or machine configuration was changed. Proposed products and effort estimates require prototypes and owner acceptance, not merely unit-test success.

## Owner decisions (2026-10-22)

The owner approved this design and answered the questions:

1. **Shape:** both. A company can run active-passive within a site, and several **sites, each with its own main and machines**, that sync under one organization (federation under a primary organization). Per-site autonomy during WAN outages follows from stage 4; the organization layer decides what crosses sites.
2. **Targets:** as close to no loss as possible, automatic recovery, and failover within **minutes**. Accepted loss: sessions started in the last ~5 minutes before a failure. Implication: streaming replication (PostgreSQL synchronous or near-synchronous standby), not daily backups, for company installs; automatic promotion with real fencing is the goal after the first release.
3. **Database:** PostgreSQL for company installs is fine; SQLite stays for personal installs.
4. **First release:** active-passive with **manual promotion** is acceptable for initial release and testing.
5. **Automatic failover (later):** fast and automated, decided by heartbeat latency and database sync lag, with an adjustable heartbeat and failover timeout. A standby promotes itself only when the primary has missed heartbeats for longer than the timeout and its own replication lag is within the allowed limit; otherwise it waits or asks a person. The old primary is fenced before the new one acts.
6. **Backup server:** any enrolled machine or an S3-compatible store can be the off-site backup target (stage 1).
